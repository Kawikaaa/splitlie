## 本轮结果

接在总额优先接口 v7 之后，继续核查保存、重开和修改链路。本轮仅本地代码与隔离内存测试，不改页面外观，不做模型调用、云端部署、数据库写入或 Git 提交/推送。

先用回归用例复现两项失败，再修复：

1. **“只记总额”仍被未完成明细阻塞。** 旧 payload 在清空明细之前先校验明细，空商品名、无效数量/金额等会使总额模式保存失败。现在先构建真正的总额载荷，再校验；商品为空、税/小费/折扣为空，相关不确定标记不混入总额记录。会话中的明细草稿不修改，切回详细模式仍可继续修正，完整明细模式仍执行严格核对。
2. **手填金额来源在重开后丢失。** 旧逻辑只比较当前金额与已存总额，重开后可能把人工金额改标为识别所得。现在保留已记录的 `amount_source: user`，修改商家或再次调整金额不会抹去人工来源；正常识别总额的来源仍能保留。

## 保存链路整理

将原 `ledgerApi.js` 中个人交易创建/更新实现原样提取到 `personalTransactionRepository.js`，原公开函数与调用参数不变。这样可向实际仓储代码注入内存客户端，验证网络失败、重试及版本冲突，而不连接或修改真实账本。

已有规则保持：

- 小票重试沿用同一操作 UUID；写入报错后，只读取本人、同空间、同 UUID 的记录。
- 只有所有发送字段与已存记录相同才恢复为成功；JSON 对象键顺序不影响比较，金额、账户或小票来源改变则不能伪装成功。
- 读取失败或找不到记录继续返回原错误；普通非小票交易不增加重试读取。
- 更新仍按交易 ID、空间 ID 和已有 `updated_at` 乐观锁限制。不在客户端实现或重复账户资金变化，余额原子性仍由数据库负责。

## 证据边界与下一步

- 内存客户端模拟 PostgREST 返回与存储行为，**不证明实际数据库唯一约束、RLS或账户余额触发器正确**；这些规则仍需要数据库/专用测试账户验收。
- “重开”用例指载荷序列化后重新读取，不是本轮已完成浏览器刷新/重新登录。
- 源码确认交易详情沿用 `ReceiptReview`：总额记录只显示总额模式说明，不显示为商品已对账。页面组件及样式本轮未更改，也没有新的视觉验收结论。
- 原图、预览、重复候选等会话信息不会进入本轮构建的小票载荷。云端关于审计字段的强约束仍未新增。
- 云端仍为已批准的 `ai-assistant` v7；本轮未改函数文件，也无需为这些前端保存修正重新部署接口。前端线上发布尚未执行。
