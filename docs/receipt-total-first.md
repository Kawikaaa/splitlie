# 小票总额优先 — 2026-11-02

## 决定与状态

用户反馈识别慢、总额提取失败、步骤多且 UI 混乱，明确选择：**先识别总额，商品明细按需**。这项最新决定调整旧规格的默认全明细流程，但不放松未知金额、最终确认、隐私和财务原子保存要求。

**本地已实现，新接口 v7 已在单独批准后部署。** 两张清晰合成小票已真实模型联调并正确填入交易表单，未保存交易。旧 v6 不接受 `receipt_summary`，安全升级提示仍保留用于回滚情形。没有数据库迁移、Secrets/模型/额度变化、真实消费外发、账务写入、前端发布或 Git 提交/推送。

## 诊断依据

- 旧流程要求一次返回并验证最多 60 行商品及税费等完整 JSON，输出上限 2800 tokens；商品结构有误时整份结果失败，总额也无法进入表单。
- 只读聚合日志中，助理接口有一次约 23.8 秒的失败；成功请求也有约 23 秒的记录。该接口混合小票与周报任务，**不能将此视为小票专属延迟评测**。
- 长票图片缩放可能影响小字可读性，属于待评测假设；本轮没有证据证明图片分辨率是总额失败的根因。

## 本地交付

1. 添加交易中的“输入记账 / 拍小票”平级；拍照页不再叠加快速文字、建议分类或再次添加面板。
2. 选择照片、预览并明确发送后，默认只提取总额、商家、日期、币种。不提取商品，也不通过求和补造总额。旋转/裁切收起，需要时再展开。
3. 结果进入现有详细表单；金额优先，可直接修改、选分类及可选关联账户。默认已支付有文字说明，付款状态可展开调整。
4. “确认并保存”就是总额模式的最终确认，不增加第二个核对勾选框。未识别到的金额留空，正数金额填写前不能保存。未识别币种会明确提示正在使用空间基准币，保存前需核对日期和币种。
5. 商品明细需主动展开后另行识别；沿用既有明细核对规则，可以切回“只记总额”。已有明细在本次草稿内复用，不重复发送；第二次识别不会覆盖用户已检查的总额、日期或币种。
6. 识别失败保留照片，提供手动填金额；取消后晚到结果不覆盖手填草稿。超过 6 秒显示实际等待说明，不制造百分比或自动重试。
7. 总额请求最多 400 输出 tokens，提供商阶段 12 秒超时、客户端 16 秒超时；完整明细保持 2800 tokens / 25 秒 / 32 秒。更短超时限制等待，也可能使拥堵时本可成功的请求转为手动回退；需要真实样本评测。

## 数据与权限

- `receipt_summary` 复用原 `receipt` 开关、鉴权、个人空间归属、每日配额与冷却；没有新开关、新权限或额度增加。明细第二次请求也消耗现有额度，不绕过冷却。
- 模型仍为当前北京百炼受限试点，不加备用模型、后台重试或外部 OCR。
- 总额保存包含 `capture_mode: summary`、`review_mode: summary`、`amount_source: recognition|user`；商品为空，税/小费/折扣为空，明确不代表商品合计已核对。手填/改过的金额标为 user。
- 使用原交易与小票 JSON 的原子保存入口。现有结构接受空商品及额外元数据；**新元数据尚未做数据库级强校验，浏览器实际保存/重开尚未验收**。不能把本地 payload 测试描述为持久化已验证。
- 完整明细仍需确定性对账或既有手动例外原因；未知金额不变零；原图只留本次会话。
