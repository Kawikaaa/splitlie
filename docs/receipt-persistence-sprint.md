### 实现与权限

- 复用真实 `TransactionModal`、`ReceiptReview`、`TransactionDetailsModal`、个人交易仓储与现有 Supabase 客户端/RLS。表单仅增加可注入的写入适配器，默认仍使用原生产函数；未改变产品控件和样式。
- 验收适配器在每次动作前重新确认当前用户 UUID、本人个人空间；只允许白名单交易/账户、指定前缀、合成来源哈希与标记。切换身份后关闭表单并停止写入。
- 识别步骤使用明确标记的模拟结果及合成图片，**不调用模型、不增加或重置配额**。先前两张真实模型结果是上一阶段证据，本轮不把模拟识别算作模型准确率。
- 默认鉴权、RLS、数据库函数与数据结构不改。不部署 Edge、不发布前端、不提交或推送 Git。
- 只读权限核查确认：普通客户端不能指定手工账户的 `id`（这是既有保护），交易 `id` 则允许用于幂等操作。两项固定账户将仅通过单独批准的 `receipt_persistence_fixture_setup.sql` 初始化；浏览器只核对结果并走原交易API，不扩展账户列权限。该初始化不作为“前端添加账户”验收证据。

### 清理与失败恢复

本轮批准需同时包含创建、修改和删除上述可丢弃合成记录的许可。结束时先删除白名单交易，验证两个合成账户余额恢复100/60，再删这两个合成账户；再次读取白名单应全为空。不会删除测试用户或个人空间。

清理只按固定 ID + 本人/同空间 + 已登记描述/账户名执行；若发现其他记录关联合成账户、来源不符或余额异常，停止清理并保留清单报告。发生中断后可按同一清单重新读取恢复，不再次重置余额或重新创建。原有测试记录不写不删。正常交易触发器会更新测试空间的更新时间，这一元数据不回拨。
