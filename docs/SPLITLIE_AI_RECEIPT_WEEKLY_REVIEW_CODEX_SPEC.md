## 1. 产品目标与总体原则

### 1.1 两个 AI 功能各自解决什么

| 功能 | 用户问题 | 价值 | 不应变成什么 |
| --- | --- | --- | --- |
| **AI Receipt Scan** | 拍下小票后还要逐笔录入商品、金额、分类 | 快速生成可审核的交易草稿，降低记录负担 | AI 自动猜金额、直接保存、另一套独立账本 |
| **AI Weekly Review** | 记了账，却只看到很多数字，不知道变化及下一步 | 总结真实变化，指出有依据的观察，并提供可选择的小行动 | 重复念数字、道德化消费评价、无依据的财务建议 |

### 1.2 统一产品闭环

`拍摄/上传小票 → AI 提取交易草稿 → 用户核对并保存 → 程序计算准确的财务事实 → 周报呈现重点变化 → 用户选择一个小行动 → 下周回顾`。

### 1.3 共同的不可妥协规则

- **AI 只负责提取、候选分类、选择有证据支持的洞察和组织表达**；金额、税费核对、账户余额、预算、退款和汇率归属由**确定性程序**处理。
- **用户最终确认**之后才能保存；AI 不能自动改账、扣款、转账、结算、创建账单或发通知。
- 用户可以不关联银行/手动账户而保存普通消费；不应强制绑定账户。
- 不得假设银行实时同步：周报必须表达“基于 Splitlie 中已记录的交易”。
- Personal 与 Shared 权限保持隔离；本轮不扩张 Shared Space。
- 保护隐私：继续采取逐次发送确认、服务端鉴权、RLS、请求配额；小票**原图不长期保存**，仅在用户确认后保存必要的结构化明细。
- 任何资金变化只发生一次：修改、删除、退款、转账等既有原子操作不能被新 AI 流程绕过。
- 五语言：English、简体中文、日本語、한국어、Español，所有新增文案走现有 i18n。

## 3. 模块 A：AI Receipt Scan 详细设计

### 3.1 产品定位与入口

- 保留现有 **Add Transaction** 体系，Scan Receipt 仅是其中一种输入方式。
- 操作选项可按现有结构组织为 **Manual / Quick Add / Scan Receipt**；若现有入口语义更清晰，可以复用，不强制三按钮。
- 扫描结果进入**现有详细交易审核/录入流程**，在其中展开 Receipt Review 区域；不要制造第二套独立的编辑与保存实现。
- 设计目标：减少反复输入、提高核对效率；不是“自动全程记账”。

### 3.2 完整用户流程

1. 用户在录入交易中选择 **Scan Receipt**。
2. 从设备选择图片或手机相机拍摄；保留预览、旋转、裁切、可放大的原尺寸查看能力。
3. 用户明确确认图片发送到 AI 服务；有取消入口。发送时使用已有配额、身份和节流保护。
4. 识别完成后生成**未保存草稿**：商家、日期、币种、商品、税费/折扣/小计/总额、候选分类等。
5. 在 Receipt Review 中核对：用户可修改每一商品行、调整总额、选择分类、账户及已付款状态。
6. 程序重新核对金额一致性；用户变更任何影响金额的字段后，原确认状态立刻失效，必须重新核对。
7. 检测疑似重复交易并提示查看；用户可以基于已有明确授权选择继续，而不是静默挡住或静默重复保存。
8. 用户确认后，通过既有原子保存流程写入**一笔交易及其结构化商品明细**。
9. 成功后可从交易详情查看/修改商品信息；刷新、重新登录后仍可读取。
10. 识别失败、网络断开、配额用尽或用户取消时，**不丢掉已填写的草稿/原图预览**；提供重试或切换手动录入。

### 3.3 Receipt Review 页面内容

**桌面推荐布局**：左侧小票原图查看区；右侧可编辑表单。两栏顶部对齐，内容可以独立按需滚动，但避免嵌套滚动和操作按钮被遮挡。右侧底部保留固定或易到达的取消/核对/保存区。

**移动端推荐布局**：上传图缩略图及“查看原图”入口在前，审核字段、商品清单、核对结果依次向下，底部稳定的确认区；可放大长票、键盘不遮挡金额输入。

**表单字段和来源：**

| 字段 | AI 行为 | 审核与保存要求 |
| --- | --- | --- |
| Merchant | 提取商家名称，可规范化表达 | 不确定时留空/标记，用户可改 |
| Transaction date | 提取日期 | 不凭扫描当日覆盖小票实际交易日；无法确定时用户确认 |
| Currency | 提取币种线索 | 缺失、冲突时用户选择；不自动猜币种 |
| Items | 提取商品名、数量、单价、行金额 | 可逐行编辑/删除/增加；必要时保留原识别文本用于核对（遵守存储策略） |
| Subtotal | 提取/显示 | 用于核对，不凭空补数字 |
| Tax / Tip / Fees | 若能看到则提取 | 分别表示；没有凭据时标记未知而非假设为零 |
| Discount | 若能看到则提取 | 明确正负语义，不与总额重复减免 |
| Total | 尝试识别 | 用户确认的核心金额；程序检查冲突与差额 |
| Category | 提供分类建议 | 可覆盖；优先复用现有用户历史默认值逻辑 |
| Payment account | 不由 AI 决定 | 用户主动选，或者不关联 |
| Payment status | 不由小票存在本身决定 | 用户确认是否已支付，保持既有资金移动规则 |

**账务建模约束**：默认 `1 张小票 → 1 笔交易 → 多条商品明细`，**不得将每条商品当作新的收入/支出记录**；后续商品级预算统计另行设计。

### 3.4 金额核对与异常状态

- 所有涉及**小计 + 税费 + 小费 − 折扣 = 应付总额**的核对，需明确是否存在舍入、多税率、不同数量单位、已含税、退款行、押金等场景；不能直接假定公式适用于所有小票。
- 若商品行与识别总额不一致，清楚显示“核对差额”及待检查字段；**不得生成虚构的杂费行去凑平**。
- 不能从识别结果证明一致时，不展示绿色“已核对”；根据已有设计要求阻止未审核保存，或让用户通过明确的人工确认流程解决例外（若要新增例外流程，先设计并测试）。
- 修改总额/商品/税费/折扣等影响核对的内容后，旧核对状态清空并重新计算。
- 在用户实际编辑的位置提示问题，而不是仅显示一个笼统错误 Toast。

**必须覆盖的异常：**

| 场景 | UI/行为 |
| --- | --- |
| 模糊/遮挡/缺页 | 提示重拍或人工填写；不能猜内容 |
| 日期/商家/币种冲突 | 高亮疑问字段，允许直接修改 |
| 不明金额/核对不一致 | 显示差额与来源，不自动凑数 |
| 可能重复 | 提示疑似重复并提供查看原记录入口；允许受控继续 |
| AI 请求超时或被取消 | 保留用户草稿，不使用迟到结果覆盖当前编辑内容 |
| 模型返回格式不合法 | 服务端验证拒绝结果；前端提供手动路径 |
| 配额耗尽/试点关闭 | 清晰提示、可继续手动记账，不显示误导性“零结果” |
| 跨币种小票 | 保存真实原币；不承诺估算 FX 等于银行入账汇率 |
| 图片与金额编辑并发 | 不允许两个识别请求/提交互相覆盖，保留现有独立 busy 状态防竞态 |

### 3.5 P1 体验增强（P0 通过后）

- 优化商家缩写与商品名称展示，避免过长文本撑坏布局；始终允许用户查看/编辑。
- **历史商家分类偏好**：优先复用用户已确认的商家/类别偏好，减少重复模型调用；新增保存/学习行为之前先检查已有数据结构与隐私范围。
- 集中呈现异常字段（例如 `2 items need review`），点按即可定位对应行。
- 商品清单长时可折叠/展开，金额核对与总额始终清晰。

### 3.6 本轮明确不做（P2 提案）

- 商品级自动细分预算、复杂税费按商品分摊。
- 扫描小票后直接生成 Shared Expense 或自动处理多人分摊。
- 长期存储原图、后台持续扫描、第三方银行自动抓取。
- 允许 AI 自动保存、不经用户确认就修改旧交易。

## 4. 模块 B：AI Weekly Review 详细设计

### 4.1 产品定位

Weekly Review 不是一篇 AI 写的作文。用户应在几十秒内回答：

1. **What happened?** 本周消费情况和上周差在哪里？
2. **What's worth noticing?** 哪一两件事情真正值得关注？
3. **What can I do?** 下周是否有一个值得尝试的小行动？

周报内容以**可解释事实为主，AI 解释为辅**。没有可靠证据时宁可不生成 Insight。

### 4.2 推荐信息架构（在已有周报上优化，不强制增加独立导航）

| 区块 | 内容 | 展示优先级 |
| --- | --- | --- |
| **Weekly Snapshot** | 选定周的净消费、记录笔数、与可比时段对比 | 最先看到 |
| **Where Your Money Went** | 主要消费类别、金额、占比，简洁图形 | 第二层 |
| **Worth Noticing** | 最多 1–2 条有依据的观察，附来源交易/统计 | 核心 AI 区块 |
| **One Small Action** | 推荐一项匹配目标的动作，接受/忽略 | 行动区 |
| **Weekly Check-in** | 上期动作完成/未完成/不适用；历史回顾入口 | 最后 |

**Overview 只预览**：本周基本统计或上一完整周的一条重要洞察 + 进入完整周报的链接。不要将整个报告、打卡日历、多个长图表全塞在 Overview。

**Review 的完整内容位置**：优先整合进现有 Weekly Recap/周总结模块，必要时提供二级完整视图；确认信息架构收益后，再决定是否新设一级 Review 页面。不要未经评估增加过多导航项。

### 4.3 Weekly Snapshot 的统计与比较

- 优先使用**已记录并被现有确定性财务引擎认可**的净消费事实，准确处理退款、收入、转账、待付款、跨币种等规则。
- 周范围和时区由现有项目的时间规则决定；显示具体日期范围。若要改变周起止定义，先给出迁移/兼容性方案。
- 上周完整 7 天与本周截至周三不能直接生成不注明限制的“周环比”。仅比较**同长度/同语义的期间**，或明确写明“截至目前/不可直接比较”。
- 缺失完整历史样本或数据加载失败时显示 `Not enough data` / `Unable to calculate`，不能显示成零消费。
- 统计说明/来源文案需表达 `Based on transactions recorded in Splitlie`；未关联银行的记录不是“自动完整财务”。

### 4.4 Worth Noticing：AI 洞察设计

**输入来源**：由服务端从登录用户合法范围的交易/周期义务中用确定性逻辑生成的候选事实；模型只选择、排序、措辞，不提供没有来源的新金额。

**最多推荐 1–2 条；没有足够值得关注的事实时显示平静的空状态，而不是硬凑观察。**

| 洞察类型 | 例子（虚构数据） | 生成前提 |
| --- | --- | --- |
| Spending Shift / 消费变化 | 本周外出就餐多花 $26，是净消费增长主要来源 | 比较期间一致、事实来源存在、差异超过合理阈值 |
| Spending Concentration / 消费集中 | 这周餐饮占已记录消费近一半 | 总额/占比可靠、样本有意义 |
| Unusual Spending / 非典型消费 | 一笔购物金额明显高于你近期同类支出 | 有可比历史，不能用少量样本轻易定义“异常” |
| Upcoming Commitments / 未来义务 | 下周有一笔已设置的周期账单接近到期 | 日期和账单状态可靠，不能冒充已启用推送 |

**不准输出的空洞/误导表述：**

- “你花了 $130，这说明你花了 $130。”
- “你的消费增加了，所以你应该节省。”（无上下文道德判断）
- “你有充足余额可以买……”（仅凭记账数据冒充银行实时余额）
- “你的财务健康分数是 82。”（无已定义的评分体系）
- “下周一定会花 $X。”（无可靠证据的预测）

**洞察组件至少显示**：标题、1–2 句说明、引用的数据/交易入口、数据范围；引用交易被编辑或删除后，应失效或提示需刷新。

### 4.5 One Small Action：将洞察变为可选行动

- **默认一周最多一个主要行动**；优先满足用户当前选择的目标，而不是同时输出多项要求。
- 文案具体、温和、可操作，不应羞辱或评判用户花钱。
- 重用现有 **Accept / Ignore（或 Not now）** 与完成反馈；若对应页面已经支持，不重复创建另一套动作存储。
- 下周反馈建议使用 `Done / Not done / Not applicable`（如果现有枚举不同，先兼容现有数据语义，避免破坏历史）。
- 不为了“保住 streak”强迫用户每天操作；连续周数仅是辅助信息。

**候选动作示例：**

| 用户目标 | 可选择行动（示例） |
| --- | --- |
| Reduce unnecessary spending | 下周回顾最常出现的非必要消费类别 |
| Stay within budget | 下次计划外购买前查看相应类别预算剩余 |
| Understand spending | 核对本周金额最大的 2–3 笔记录 |
| Manage subscriptions | 检查即将到期的已记录订阅 |
| Build a tracking habit | 下周尽量及时记录高金额消费 |

**注意**：只建议用户确实有数据支持、在产品内能执行或合理完成的行动。不得未经授权自动创建预算、提醒、订阅或财务交易。

### 4.6 生成与缓存/失效策略

1. 继续以**用户主动生成**为默认，不加自动邮件、手机推送或后台定时 AI 生成。
2. 当前周未结束时，可展示截止目前的**规则统计**；完整 AI 周报优先面向结束的周，清楚标明时间边界。
3. 对同一周重复打开时，优先读取已保存且仍有效的报告，不无谓重复调用模型。
4. 用户修改、删除、补记相关时段交易、退款、分类、账单数据后，依据现有过期机制将受影响报告标记为需要更新；不显示过期洞察为最新结论。
5. AI 不可用时仍展示确定性统计、可用历史与清晰的重试/回退信息。
6. 生成中显示可理解的 Loading；失败不清空旧报告、不锁死目标设置或行动反馈。
7. 只通过本人权限可访问的事实产生报告，并保留当前隐私/存储/来源规则。

### 4.7 周报视觉规范

- 不是聊天窗口；使用与现有页面一致的卡片、留白、字体与轻量图形。
- 标题层级清晰：金额/核心概况 > 重要洞察 > 小行动 > 详细依据与历史。
- 不要超过 **1–2 条主洞察和 1 个主行动**，非重要统计允许折叠。
- 可点击来源明细、可看到数据日期和币种；事实/估算/AI 建议明确区分。
- 避免无根据的绿色/红色“消费好坏”判断。

## 5. 财务语义与数据一致性（两模块共用）

**不得直接重写财务引擎**。首先复用既有确定性服务，必要时添加局部适配和测试。

| 事件 | 小票侧 | 周报侧 |
| --- | --- | --- |
| 普通已支付支出 | 用户确认后写入一笔交易；账户影响一次 | 按既有净消费规则计入 |
| 未支付支出 | 由用户明确设置；不提前扣账户资金 | 区分真实已付消费与计划预留，避免重复 |
| 收到退款 | 从原交易的退款流程处理，不当新收入 | 按**退款收到日期**冲减相应消费，不回写旧月份 |
| 账户转账 | 不在普通小票支出流程中误创建转账 | 不计收入、不计消费、不改变 Safe to Spend |
| 信用卡还款 | 本轮不新建还款能力 | 即使未来加入也不得重复算消费；**目前还款 UI 未实现** |
| 跨币种 | 保留交易原币与已确认金额 | 基于已验证的换算来源、时点说明估算；不猜汇率 |
| Shared | 不直接生成共享分摊记录 | 暂不假设共享总账单全算个人消费；后续仅本人份额受控同步 |
| 交易编辑/删除 | 保证原子修正余额与商品明细 | 相关报告或统计必须相应更新/过期 |

**特别注意**：把“小票商品行”计为多笔消费、把退款计为收入、把转账计为支出、把 Shared 全额计为 Personal、把账户余额当 Safe to Spend，全部属于不可接受的逻辑错误。

## 9. 必须通过的验收用例（Acceptance Criteria）

### Receipt — 用户级

1. **正常小票**：识别商家、日期、真实币种、商品与总额；用户修改任一商品/总额后可重新核对，并只保存一次。
2. **不一致小票**：提示差额并阻止错误自动保存；用户可查看原图、手动修正，不制造虚构费用。
3. **无账户**：普通消费可以不关联账户保存；计划与消费统计生效但账户余额不动。
4. **已关联账户**：已付支出按既有引擎影响余额恰好一次；修改/删除能原子撤销。
5. **重复上传**：可识别疑似重复并查看原记录；受控继续时仍不得出现无意重复提交。
6. **失败/取消/限额**：输入不丢失，不出现错误保存或后到旧请求覆盖。
7. **持久化**：刷新、再次登录、查看交易详情、编辑商品后内容一致；图片没有违背不长期保存策略。
8. **权限**：跨用户/跨 Space 无法读取、修改、通过来源链接泄露财务资料。

### Weekly Review — 用户级

1. **数据准确**：周报金额、交易数、分类占比与确定性引擎一致；用户看得到统计期间及依据。
2. **可比性**：当前部分周不被伪装成完整周环比；数据不足时不生成虚假增长。
3. **财务语义**：退款、转账、未付、不同币种及信用卡不会重复或错误计入消费。
4. **有用内容**：最多两条有根据的 Worth Noticing，且有证据链接；无洞察时不勉强生成。
5. **可选行动**：最多一个主行动，可接受/忽略，并能在下一周反馈；不会自动改账。
6. **数据变化**：编辑/删除/补记交易会令受影响历史周报过期，不把陈旧建议当作实时事实。
7. **失败回退**：模型失败时基础周统计仍可用，不冲掉历史内容；显示重试途径。
8. **隐私**：只读取本人授权数据，来源链接遵守 RLS。

### 通用质量门槛

- 所有既有测试通过，新增覆盖异常处理与财务不变量。
- `npm.cmd test` / `npm.cmd run build`（适配实际运行环境）通过；`git diff --check` 无问题。
- 至少桌面 1280×720 + 手机 390×844 检查；五语言布局和文案合理。
- 无未授权数据库/生产部署/额度修改；无污染真实账本的测试数据。
- 无一行卡片上下不对齐、间距混乱、焦点边框被裁切、底部操作按钮无法到达等退化。

## 11. 范围控制与产品判断

此次迭代成功的标志不是多了几个 AI 按钮，而是：

- 用户拍完小票，**更快而且更准确地完成一笔可追溯的记账**。
- 用户看完周报，**理解本周最重要的变化，并能够选择一个现实可行的小行动**。
- AI 内容与真实账本、账户余额、计划规则、权限和后续编辑**永远保持一致**。
- 当前模型效果未通过充分评测之前，**不应宣称高准确率，不要因为追求“智能”而牺牲可信度**。

**实现原则：先把 P0 可靠性做好，再做 P1 UI/洞察升级；P2 暂不扩张。**
